Searchzen

SEO rank tracker and site audit software as a service, built with Next.js 16, React 19 and Tailwind CSS 4. Your customers track their Google positions by country, city, language and device, crawl their websites for technical SEO problems, connect Google Search Console and share white-label reports with their clients. This guide takes you from a fresh clone to a live platform with paying customers.

Quick start: upload the app folder, run npm install and npm run build, start the app, then open your domain in a browser. The web installer does the rest. Then read Background jobs (rank checks and audits run in the background) and SERP providers: without a SERP provider no rankings are checked.

Introduction

Searchzen lets you run your own SEO platform, in the style of SE Ranking, Serpstat's rank tracker or Ahrefs' site audit. Your customers sign up, add their websites as projects and get four tools for each one:

  • Rank tracking. They add keywords (one by one, pasted, from a CSV file or through the REST API) with a country, language, optional city and a device. Searchzen checks every keyword daily or weekly and shows the position, the ranking page, the SERP features on the results page, their competitors' positions, a visibility score and the history. Alerts tell them when a keyword enters or leaves the top 3/10/100, moves a lot, or when the page they want to rank stops ranking.
  • Site audit. A polite crawler reads the site like a search engine (it obeys robots.txt), runs 57 checks (broken pages and links, redirects, titles, descriptions, headings, canonicals, hreflang, sitemaps, HTTPS, speed, structured data, social tags…) and computes a health score from 0 to 100, with the change since the previous audit.
  • Google Search Console. With one click (Google sign-in) customers import clicks, impressions, CTR and average position, with their top queries and pages.
  • Client reports. A read-only report link (optionally password-protected) with rankings, the audit and Search Console data, saved as PDF from the browser, emailed weekly or monthly, with the agency's own logo and colour on white-label plans, plus an embeddable SEO health badge.

Rankings come from a SERP data provider that you, the administrator, choose and pay for: Serper.dev, SerpApi, DataForSEO or ValueSERP. Searchzen never scrapes Google itself. You earn money with paid plans that limit projects, tracked keywords, the check frequency, audit size and count, and unlock Search Console, the REST API and white-label reports. Your customers pay through Stripe (automatic renewal), PayPal, Razorpay or bank transfer.

Words used in this guide: you or the administrator run the platform. Customers (users) sign up on your platform and create projects. Clients are your customers' own clients who receive reports. In the examples your platform lives at https://seo.example.com and a customer's website is example-shop.com.
Rank data costs money. Every keyword check is one or more paid requests to your SERP provider. Read Depth & cost before you set plan prices and keyword limits.

Installation

Pick the guide that matches your hosting. Every method ends with the web installer, and every method needs a way to run background jobs: read Background jobs right after installing, then choose a SERP provider.

Install Searchzen on its own domain or subdomain, for example https://seo.example.com. Shared report links, the badge snippet on customers' websites, the Google sign-in redirect address and the cron URL all contain this address, so changing it later means customers must update their badge snippets and you must update the redirect URI in Google Cloud.

cPanel / shared hosting (Setup Node.js App)

  1. In cPanel open MySQL® Databases. Create a database and a user, then add the user to the database with All privileges. Write down the database name, username and password.
  2. Create the subdomain (e.g. seo.example.com) in Domains and turn on SSL/TLS Status → Run AutoSSL so it has HTTPS.
  3. Open File Manager and upload searchzen.zip (the app folder of the repository, renamed to searchzen and zipped) to your home folder, e.g. /home/youruser/searchzen, and extract it. Do not put it inside public_html.
  4. Open Setup Node.js App → Create Application:
    • Node.js version: the newest available (22.x recommended)
    • Application mode: Production
    • Application root: searchzen
    • Application URL: your domain or subdomain
    • Application startup file: server.js
    Click Create.
  5. Click Run NPM Install and wait until it finishes.
  6. Copy the command shown at the top of the page (it looks like source /home/youruser/nodevenv/searchzen/22/bin/activate && cd /home/youruser/searchzen). Open Terminal in cPanel, paste it, then run: 
    npm run build
    The build takes 1–4 minutes. It first prints [badge] public/sz-badge.js … B gzip (the badge script), then builds the app.
  7. Back in Setup Node.js App, click Restart. Open your domain: you will see the installer.
  8. After installing, add the cron job from Admin → System (see Cron URL). On cPanel this is strongly recommended: Passenger stops idle apps, and lazy mode only runs while there is activity, so keyword checks and audits would stall at night.

server.js starts the built Next.js app, which serves everything: pages, shared reports, the API, the badge and the files in public. You don't need to copy anything into public_html.

If the build stops with “JavaScript heap out of memory” your plan limits memory. Build on your own computer instead (npm install && npm run build), then upload the whole folder including the .next folder and public/sz-badge.js, and only run “Run NPM Install” + “Restart” on the server.
Shared hosting often limits how long a request may run and how many processes you get. Site audits are crawled in short slices (see How the crawler works), so they work there too, just more slowly than on a VPS.

VPS (Ubuntu) with PM2 and Nginx

  1. Install Node.js 22, Nginx and PM2: 
    curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs nginx
sudo npm install -g pm2
  2. Install MySQL (or use SQLite and skip this step): 
    sudo apt install -y mysql-server
sudo mysql -e "CREATE DATABASE searchzen CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'searchzen'@'localhost' IDENTIFIED BY 'choose-a-strong-password';
GRANT ALL PRIVILEGES ON searchzen.* TO 'searchzen'@'localhost'; FLUSH PRIVILEGES;"
  3. Upload the app folder to /var/www/searchzen, then build: 
    cd /var/www/searchzen
npm ci
npm run build
  4. Choose a cron secret and start the app and the worker with PM2. ecosystem.config.cjs starts two processes: searchzen (the web app) and searchzen-worker (runs the background jobs every 15 seconds). Both get the same CRON_SECRET: 
    export CRON_SECRET="$(openssl rand -hex 24)"
echo "$CRON_SECRET"          # keep a copy
pm2 start ecosystem.config.cjs
pm2 save && pm2 startup

    Always set your own CRON_SECRET before pm2 start. Without it the worker can't run jobs (PM2 prints a warning and the worker exits), and a CRON_SECRET line in .env.local is only seen by the worker, not by the app. Export the variable before pm2 start (as above) or write your secret into ecosystem.config.cjs. Use at least 12 random characters: the app ignores shorter values and the example value change-me-to-a-long-random-string. After changing it run pm2 restart ecosystem.config.cjs --update-env.

  5. Create /etc/nginx/sites-available/searchzen: 
    server {
    listen 80;
    server_name seo.example.com;
    client_max_body_size 10m;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_read_timeout 90s;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}
    X-Forwarded-For is used for rate limits (sign-in, registration, the cron URL, the REST API, the badge). proxy_read_timeout 90s leaves room for “Check now” and the cron URL, which can work for up to 45 seconds. Enable the site and add a free SSL certificate: 
    sudo ln -s /etc/nginx/sites-available/searchzen /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d seo.example.com
  6. Open https://seo.example.com to run the installer. Afterwards, Admin → System → Scheduler should show Running with the source worker within a minute.
Keep instances: 1 for the web app in ecosystem.config.cjs: rate limits are kept per process. If you ever run several app servers, set the same APP_SECRET and NEXT_SERVER_ACTIONS_ENCRYPTION_KEY on all of them. The worker calls http://localhost:3000 by default; set WORKER_URL if the app listens elsewhere.

Docker

The app folder includes a Dockerfile and a docker-compose.yml with three services: app (the web app), worker (runs background jobs every 15 seconds) and db (MySQL 8.4). First create a file named .env next to docker-compose.yml with your own secret:

CRON_SECRET=paste-a-long-random-string-here

Then start everything:

cd searchzen
docker compose up -d --build

Open http://your-server:3000. In the installer choose MySQL with host db, port 3306, database searchzen, user searchzen, password searchzen (change these and MYSQL_ROOT_PASSWORD in docker-compose.yml first). The storage folder (configuration, the generated app secret and uploads) is kept in a Docker volume. Put Nginx, Caddy or Traefik with HTTPS in front of port 3000, and make sure it sends X-Forwarded-For.

docker-compose.yml refuses to start until CRON_SECRET is set in the .env file next to it (at least 12 random characters). The included .dockerignore keeps local node_modules, .next and storage folders out of the image.

Without Compose:

docker build -t searchzen .
docker network create searchzen-net
docker run -d --name searchzen --network searchzen-net -p 3000:3000 \
  -e CRON_SECRET=your-secret -v searchzen-storage:/app/storage searchzen
docker run -d --name searchzen-worker --network searchzen-net \
  -e WORKER_URL=http://searchzen:3000 -e CRON_SECRET=your-secret searchzen node scripts/worker.mjs

Vercel (with TiDB Cloud or another cloud MySQL)

Vercel has no permanent disk, so the web installer and SQLite can't be used there. Instead, Searchzen is configured with environment variables and a cloud MySQL-compatible database such as TiDB Cloud Serverless (free tier), Aiven or PlanetScale.

  1. Create a database. In TiDB Cloud: create a Serverless cluster in the region closest to your Vercel functions, open Connect, generate a password and note the host, port (4000), user and password. In the SQL editor run CREATE DATABASE searchzen;
  2. Fork this repository on GitHub (or push your copy to your own repository).
  3. In Vercel click Add New → Project, import the repository and set Root Directory to app (the folder that contains package.json). Keep the default build command (npm run build): it also builds sz-badge.js.
  4. Add these Environment Variables: 
    DB_DRIVER=mysql
DB_HOST=gateway01.ap-southeast-1.prod.aws.tidbcloud.com
DB_PORT=4000
DB_USER=xxxxxxxx.root
DB_PASSWORD=your-password
DB_NAME=searchzen
DB_SSL=true
APP_INSTALLED=true
ADMIN_EMAIL=you@example.com
ADMIN_PASSWORD=a-strong-password
ADMIN_NAME=Your Name
SITE_URL=https://seo.example.com
CRON_SECRET=a-long-random-string
APP_SECRET=another-long-random-string
    Instead of the DB_* variables you can set one DATABASE_URL=mysql://user:password@host:4000/searchzen?ssl=true. Optionally add your SERP key here too (e.g. SERPER_API_KEY and SERP_PROVIDER=serper, see Where to paste keys).
  5. Click Deploy. Tables are created automatically on the first visit and the administrator account is created from ADMIN_EMAIL / ADMIN_PASSWORD.
  6. Add your domain in Settings → Domains, and set the same address in Admin → Settings → General → Site URL.
  7. In Vercel open Settings → Functions and choose the region closest to your database.
  8. Set up the scheduler as described in Vercel & serverless. This step is not optional on Vercel: without it, keywords are checked and audits crawled only while someone uses the site.

Vercel is fine for a demo or a small platform. Keep in mind:

  • Set APP_SECRET (16+ random characters). It encrypts the Google Search Console tokens; without it the app falls back to a secret stored in the database, which works, but an explicit value is safer and survives a database move. See APP_SECRET.
  • There is no worker process, so background jobs depend on an external cron service. Vercel Hobby cron runs only once a day.
  • Uploaded files (logos) are not kept (no permanent disk). Paste image URLs instead of uploading.
  • Rate limits are kept per serverless instance.

Local computer (for testing or customising)

cd searchzen
npm install
npm run dev

Open http://localhost:3000 and choose SQLite in the installer. Lazy mode is on by default, so background jobs run while you click around. To run them without visiting pages, start the worker in a second terminal (copy the secret from Admin → System → Scheduler):

CRON_SECRET=the-secret-from-admin npm run worker

On Windows PowerShell: $env:CRON_SECRET="the-secret"; npm run worker.

To try rank tracking without paying for a SERP provider, switch on Allow the Simulated provider in Admin → Settings → Rank tracking and choose Simulated. It produces realistic but fake positions (see Simulated provider). Switch to a real provider before customers sign up. The site audit crawler refuses local and private addresses (localhost, 127.0.0.1, 192.168.x.x…), so audit a public website even when testing locally.

Web installer

  1. Server requirements – checks the Node.js version and that storage is writable.
  2. Database – choose MySQL/MariaDB (host, port, database, user, password, and Use SSL for cloud databases such as TiDB Cloud, Aiven or DigitalOcean) or SQLite. Click Test connection, then continue.
  3. Site and administrator – enter your platform name, the full site URL (e.g. https://seo.example.com) and the administrator account. Click Install now.

The installer creates all tables and indexes, the three default plans (Free, Pro, Agency), the default content pages (such as the Privacy policy and Terms of service) and starter blog posts. It writes storage/config.json and locks itself (storage/installed.lock). Sign in at /login. The admin panel is at /admin, the customer dashboard at /dashboard, shared reports at /r/<token>.

Background jobs & scheduling

Pages, the API and shared reports answer immediately; that never depends on the scheduler. But the real work of an SEO platform happens in the background, and something must start it. Read this chapter before you invite customers: without background jobs, keywords are never checked, audits stay at “queued”, and Search Console data is not imported.

The jobs

A tick runs these jobs one after the other, within a time budget. Each job does a small slice of work and remembers when it should run again, so ticks every 15 seconds are cheap. Whatever doesn't fit is picked up by the next tick. A lock in the database makes sure two ticks never run at the same time.

JobWhat it doesHow often
rank-checksChecks the keywords that are due (active keyword, active project, active owner) with the SERP provider: up to Checks per run keywords (default 40), Parallel requests at a time (default 3), within Time per run (default 20 s). Saves the day's position, the competitors' positions, the SERP features and the top 20 results, then sends alerts. Stops and pauses all checks after a wrong key or empty credits (see Pause on errors).Every tick
auditsStarts scheduled audits (projects set to weekly or monthly audits; checked every 15 minutes), then crawls and analyses running audits, oldest first, at most 20 seconds per audit per tick so several audits share the time.Every tick
gsc-importImports Search Console data: the 90-day history of newly connected properties (10 days per step), then a daily refresh of the last 3 days. Deletes rows older than about 16 months once a day.Every tick while a history import runs, otherwise every 10 minutes
reportsSends scheduled client report emails that are due (weekly on Mondays, monthly on the 1st, at 07:00 UTC), up to 20 per run.Every 5 minutes
digestSends the weekly digest from Monday 07:00 UTC, once per account and week, in batches of 25. Waits while SMTP isn't configured.Every 30 minutes
housekeepingDeletes expired sessions and password reset links, alert log entries older than 90 days and saved results pages (SERP snapshots) older than 30 days. Rankings themselves are kept.Every hour
Without ticks no keyword is checked (the rankings stay “Pending”), audits stay queued, Search Console data isn't imported and no report emails or digests are sent. Note: while someone keeps the audit page open, the page itself drives that audit forward, so audits can seem to “work” during testing even without a scheduler.

There are four ways to start ticks:

MethodHow oftenBest for
Lazy mode (on by default)When the platform serves one of its pages and no tick ran for a minute. Only while there is activity, and with a short 8-second budget.Trying Searchzen.
Cron URLEvery time the URL is opened: every minute is recommended.cPanel, shared hosting, Vercel (with an external cron service).
Worker (npm run worker)Every 15 seconds.VPS and Docker. Best for many keywords and big audits.
Run jobs nowWhen you click the button in Admin → System. Ignores the jobs' own intervals.Testing.

The methods can be combined safely. A tick started while another is running simply does nothing.

How much can one tick do? With the defaults, one tick checks up to 40 keywords. With the worker (4 ticks a minute) that is up to about 9,600 checks an hour; with a cron job every minute about 2,400 an hour. Big platforms can raise Checks per run and Parallel requests in Admin → Settings → Rank tracking (see Run limits).

The cron secret

The cron URL and the worker are protected by a secret:

  • If the environment variable CRON_SECRET is set (at least 12 characters, not the example value), that value is the secret.
  • Otherwise Searchzen creates a random secret the first time it is needed and stores it in the database.

To see it, open Admin → System. The Scheduler card shows the complete Cron URL (with a Copy button) and a ready-made cron line. Click New secret to replace a stored secret, e.g. if it leaked; the old URL stops working immediately, so update your cron job and worker. The button is hidden while the secret comes from CRON_SECRET: change the environment variable instead and restart.

The secret can be sent in two ways:

curl -fsS "https://seo.example.com/api/cron/tick?key=YOUR-SECRET"
curl -fsS -H "Authorization: Bearer YOUR-SECRET" https://seo.example.com/api/cron/tick

GET and POST both work. A correct call answers with a JSON summary, for example {"source":"cron","startedAt":"…","jobs":{"rank-checks":40,"audits":120,"gsc-import":3,"reports":0,"digest":0,"housekeeping":0},"failed":[],"skipped":[],"durationMs":21840,"skippedLocked":false}. The numbers are the items each job handled (keywords checked, pages crawled, import steps, emails sent, rows cleaned up). A wrong or missing secret answers 401. More than 30 calls per minute from one IP address answer 429. "skippedLocked":true means another tick was still running.

Lazy mode (default, no setup)

With Admin → Settings → SEO tools → Run background jobs on visits switched on, the platform runs a tick after it has answered a page request, whenever no tick ran during the last minute. The visitor never waits. A lazy tick has an 8-second time budget, and each server process tries at most once every 15 seconds.

Lazy mode only works while people use the platform. At night, or on a new platform, nothing may run: daily rank checks happen late, audits pause, report emails are late. On cPanel, Passenger also stops the app after a period without requests. Use it to get started, then add the cron URL or the worker. You can leave lazy mode on as a backup: it does nothing while cron or the worker keep ticks fresh.

Cron URL

SERP providers

Searchzen reads Google results through a SERP data provider: a company that runs Google searches for a given country, language, city and device and returns the results as JSON. You choose one provider for the whole platform in Admin → Settings → Rank tracking, and every keyword check of every customer goes through it. Customers never see or need a provider key.

Searchzen never scrapes Google. The app sends no requests to Google Search itself and has no scraping, proxy or CAPTCHA code. Positions come only from the provider's official API (or from the Simulated provider, which invents them). This keeps your servers' IP addresses out of trouble and makes results reliable, but every check costs the provider's price per request.
Until you choose a provider (and paste its key), no keyword is checked. Customers see “Rank checks aren't set up on this site yet”, and as an administrator you see a notice with a link to the settings. Keywords stay saved and are checked as soon as a provider works.

Depth and cost

Depth is how many results Searchzen reads per keyword: 10, 20 (default), 50 or 100. A keyword not found within the depth shows as “20+” (for depth 20) and counts as not ranked.

DepthRequests per check (at most)Notes
101Cheapest. Only page 1: keywords beyond #10 show as “10+”.
202Recommended. Pages 1–2, where most keywords that matter are.
505Up to 5× the cost of depth 10.
10010Up to 10× the cost of depth 10. Use with care.

Paging stops early once the project's domain and every competitor domain have been found, or when Google has no more results. A keyword at #3 in a project without competitors costs one request even at depth 100; a keyword that doesn't rank always costs the full depth. Competitors therefore make checks more expensive: paging continues until all of them are found.

Estimate your monthly requests

requests per month ≈ keywords × checks per month × pages per check
checks per month: daily ≈ 30, weekly ≈ 4.3
pages per check: between 1 and depth ÷ 10

Example: a customer on the default Pro plan with 300 keywords checked daily at depth 20 needs between 9,000 and 18,000 requests a month (300 × 30 × 1 to 2). The same keywords checked weekly need between about 1,300 and 2,600. Multiply by your expected number of customers, then look up the provider's price per 1,000 requests on its pricing page. Then:

  • Set plan limits (tracked keywords, daily or weekly checks) so a full plan costs you clearly less than its price. Plans that check weekly cost about 7 times less.
  • Keep the depth at 20 unless your customers really need positions beyond page 2.
  • “Check now” (dashboard and API) runs extra checks. They are limited (see Rankings) but still cost requests.
  • Watch Provider usage (last 30 days) on the same page: requests, errors and credits (DataForSEO: cost in USD) per provider and day. The admin dashboard shows the number of rank checks per day.

The Simulated provider generates realistic but fake positions without any API: smooth random walks per keyword and day (the same keyword gives the same result on the same day), some keywords that never rank, competitors with their own walks, plausible ranking URLs and SERP features. It is meant for demos and for trying the dashboard, alerts and reports.

  • In demo mode (DEMO_MODE=true) it is used automatically when no other provider is chosen.
  • Outside demo mode you must switch on Allow the Simulated provider (testing only) before you can select it.
  • While it is in use, the rankings pages show “Positions here are simulated test data, not real Google rankings.”
Never use the Simulated provider for real customers. Its numbers have nothing to do with Google.

Google Search Console setup

Customers on plans with Google Search Console can connect their Google account and import clicks, impressions, CTR, average position, queries and pages. For this, you create one OAuth client in Google Cloud for your platform (free) and paste it into Admin → Settings → Google. Customers then click Connect with Google, approve read-only access and pick their property.

Searchzen asks Google for these scopes: openid, email (to show which Google account is connected) and https://www.googleapis.com/auth/webmasters.readonly (“View Search Console data for your verified sites”). It never writes to Search Console.

1. Create a Google Cloud project and enable the API

  1. Open console.cloud.google.com and sign in with the Google account that should own the app (ideally a company account).
  2. Click the project selector at the top → New project. Name it, e.g. Searchzen, and click Create. Make sure the new project is selected.
  3. Open APIs & Services → Library, search for Google Search Console API, open it and click Enable.

2. Configure the OAuth consent screen

Google's console calls this Google Auth Platform (older versions: OAuth consent screen).

  1. Open APIs & Services → OAuth consent screen (or Google Auth Platform → Branding) and click Get started / Configure.
  2. App information: app name (your platform name, e.g. Searchzen or your brand) and a user support email.
  3. Audience / User type: choose External, so any Google account can connect (Internal is only for accounts in your own Google Workspace).
  4. Contact information: your email. Accept the policy and create.
  5. Branding: add your logo (optional), the application home page (https://seo.example.com), the privacy policy link (https://seo.example.com/p/privacy-policy or wherever your policy is) and the terms of service link, and add your domain (example.com) under Authorized domains.
  6. Data access / Scopes: click Add or remove scopes and add .../auth/webmasters.readonly (Google Search Console API), plus openid and .../auth/userinfo.email. Save.

3. Testing vs. production, and the “unverified app” warning

A new app starts in the Testing publishing status:

  • Only the test users you add under Audience → Test users (up to 100 Google accounts) can connect. Anyone else gets Google's Error 403: access_denied page.
  • Google lets refresh tokens of Testing apps expire after 7 days. Imports then stop and customers see Disconnected and must reconnect. Testing is therefore only for trying the integration.

For real customers, click Publish app (Audience → Publishing status → In production). Because webmasters.readonly is a sensitive scope, Google shows a “Google hasn't verified this app” warning until your app is verified; users can still continue with Advanced → Go to (your app), and unverified apps are limited in the number of users. To remove the warning, submit the app for verification in the console (Verification Center). Google typically asks for:

  • a verified domain (Google Search Console ownership of your platform's domain) and a public home page on it;
  • a privacy policy on that domain that describes how you use Google user data (see Search Console data & Limited Use);
  • a short explanation and often a demo video of how the scope is used: the customer clicks Connect with Google on the Search Console tab, approves, picks a property and sees the imported clicks, impressions and queries.

Verification can take from a few days to several weeks. Read Google's current requirements in the console; they change from time to time.

4. Create the OAuth client

  1. Open APIs & Services → Credentials (or Google Auth Platform → Clients) → Create credentials → OAuth client ID.
  2. Application type: Web application. Name: e.g. Searchzen web.
  3. Under Authorized redirect URIs add exactly: 
    https://seo.example.com/api/gsc/callback
    It is your Site URL followed by /api/gsc/callback. Admin → Settings → Google and the dashboard's setup notice show the exact value for your installation. It must match character for character: https vs http, www or not, no trailing slash. Authorized JavaScript origins is not needed.
  4. Click Create and copy the Client ID (…apps.googleusercontent.com) and the Client secret (GOCSPX-…).
  5. In Searchzen open Admin → Settings → Google, paste both and save.
  6. Test it: open a project in /dashboard (administrators have every plan feature), open the Search Console tab and click Connect with Google. In Testing mode, use an account you added as a test user.
If you change your Site URL (new domain, adding www), add the new redirect URI in Google Cloud too. Google can take a few minutes to apply changes to a client.

5. APP_SECRET (encryption of Google tokens)

The Google refresh token of every connected account is stored encrypted (AES-256-GCM) in the database. Access tokens are kept in memory only. The same secret also signs the OAuth “state” of the sign-in flow and the unlock cookies of password-protected reports. Searchzen takes the secret from, in this order:

  1. the environment variable APP_SECRET (at least 16 characters);
  2. appSecret in storage/config.json, generated automatically on first use on normal installations;
  3. an app_secret row in the database, when storage/config.json can't be written (read-only hosting without APP_SECRET).

Set APP_SECRET yourself (e.g. openssl rand -hex 32) on Vercel and other serverless hosts, when you run more than one app server or container, and when servers don't share the same storage folder. Otherwise each server could generate its own secret, and tokens encrypted by one server can't be read by another.

Never change or lose the secret once customers have connected Google. With a different secret the stored tokens can't be decrypted: imports stop with “The stored Google token can't be read (the app secret changed). Reconnect the account.” Back up storage/config.json (or your APP_SECRET) together with the database.

The visibility score

Visibility estimates how many clicks the keywords get compared with the best case. Each position has an expected click-through rate (CTR): position 1 ≈ 28 %, 2 ≈ 15.5 %, 3 ≈ 10 %, 4 ≈ 7 %, 5 ≈ 5.2 %, falling to 1.7 % at position 10 and 0.5 % at 20; positions 21–50 count 0.2 %, 51–100 count 0.05 %, not ranked 0.

visibility = Σ expected CTR(position of each keyword) ÷ (number of keywords × 28 %) × 100

So 100 % means every keyword ranks #1; a project where every keyword is at #10 scores about 6 %. The score is shown with one decimal. The chart shows visibility and average position per day; days without a check carry the previous position forward for up to 8 days.

Keyword table and keyword page

Filter by search text, tag and status; Export CSV downloads the table. A keyword's page shows: first and best position, average, last check (and the last error, if a check failed), the position history chart, daily positions, ranking-URL changes, the competitors' positions, the SERP features seen per check, and the latest results page (the top 20 results of the last check, kept for 30 days).

Site audit

Open Site audit and click Start audit, or schedule audits weekly or monthly in Project settings → Site audit. While it runs, the page shows the progress (“120 of 500 pages crawled”, URLs waiting). The crawl runs in the background; keeping the page open makes it faster. When it finishes you get the health score, the issues by severity and category, the site checks (robots.txt, XML sitemap, HTTPS, http → https redirect, start URL), the list of issues and the list of pages.

How the crawler works

  1. Start. It opens https://<domain>/ (falling back to http://) and follows redirects; a redirect to www. or another subdomain of the same site decides the host that is crawled. A redirect to another site fails the audit.
  2. robots.txt. It reads /robots.txt and obeys the rules for SearchzenBot (or *), with Google's matching rules: the most specific user-agent group, the longest matching rule wins, * and $ wildcards. A Crawl-delay is honoured (up to 10 seconds). If robots.txt blocks the start page, the audit fails with “robots.txt does not allow SearchzenBot to crawl the start page.”
  3. Sitemaps. It reads the sitemaps listed in robots.txt, or /sitemap.xml and /sitemap_index.xml (sitemap indexes, gzip and plain-text sitemaps are understood). Their URLs are added to the queue, so pages without links are crawled too.
  4. Crawl. It fetches pages breadth-first (closest to the home page first), 3 at a time, or one at a time with a pause when a crawl delay applies. It follows internal links up to 10 clicks deep, plus canonical and hreflang targets. Images, scripts, styles, fonts, videos and archives are skipped. Up to 3 MB of HTML per page is read; each request has a 10-second timeout. The first 50 external links found are checked with a HEAD request (confirmed with GET).
  5. Analyse. When the queue is empty or the page limit is reached, it computes internal links (inlinks) and click depth, runs the 57 checks, stores the issues and the health score, compares with the previous audit and sends the audit alert.

The crawl is resumable: it runs in short slices from the scheduler (and from the open audit page), keeps its queue in the database and holds a 90-second lock per audit so two workers never crawl the same audit. If a server restarts mid-crawl, the next tick continues where it stopped; pages already stored are never fetched twice. An audit running longer than 24 hours is stopped. Only one audit per project runs at a time.

Audit checks

The audit runs these 57 checks: 9 critical, 24 warnings and 24 notices. Page checks run on every crawled page (content checks only on HTML pages that answered 200); the 8 site-wide checks run once per audit. Duplicate checks (titles, descriptions, H1) and thin content only look at indexable pages (200, no noindex, canonical to itself). Thresholds: title 30–60 characters, meta description 70–160 characters, thin content under 200 words, more than 150 links, URL longer than 115 characters, deeper than 4 clicks, HTML over 1 MB, time to first byte over 1.5 s, more than 25 scripts.

Health score

The health score (0–100) summarises an audit. Each page-level issue has a weight by severity (critical 10, warning 3, notice 0.5); site-wide issues cost a fixed number of points (critical 8, warning 3, notice 1, at most 30 points together):

density = Σ weights of all page-level issues ÷ pages crawled
page score = 100 ÷ (1 + density ÷ 10)
penalty = min(30, Σ site-wide penalties)
health score = round(page score − penalty), between 0 and 100

A site with no issues scores 100. On average one critical issue per page halves the page score (50); one warning on every page gives 77; one notice on every page 95. A missing sitemap (warning, −3) or no HTTPS (critical, −8) costs the same on a small and a large site. Grades: Good 80–100 (green), Needs work 50–79 (amber), Poor below 50 (red).

Search Console tab

Requires a plan with Google Search Console and the administrator's Google setup.

  1. Open the project's Search Console tab and click Connect with Google. Sign in, allow “View Search Console data for your verified sites”.
  2. Back in Searchzen, the property is picked automatically when exactly one property matches the project's domain (a domain property sc-domain:example-shop.com is preferred). Otherwise choose it in Choose the Search Console property; properties that match the domain are marked ✓.
  3. The last 90 days are imported right away (newest first, 10 days per step), then the last 3 days are refreshed once a day. Search Console data is about two days behind.

The tab shows clicks, impressions, CTR and average position for 7, 28 or 90 days, a chart, and the top queries and pages (up to 250 queries and 100 pages per day are stored), with a filter and CSV export. Track adds a query to the tracked keywords in one click. Import now refreshes immediately. One Google account can serve several projects; Connect another Google account adds more. Remove detaches the property from the project and deletes its imported data; Disconnect (under Google accounts) revokes Searchzen's access at Google and stops all projects that used that account (their imported rows are kept). If Google stops accepting the access (the user removed it in their Google account, changed their password, or didn't use it for six months), the connection shows Disconnected, imports stop and the owner gets one email: click Reconnect.

System & scheduler

Search Console data & Google's Limited Use requirements

When you publish your Google OAuth app, Google requires that your use of data from Google APIs follows the Google API Services User Data Policy, including the Limited Use requirements. Searchzen is built for this:

Your privacy policy must say this too (the default page does), and you must not use the data for anything else, for example training models or building marketing lists. Your staff should only look at customers' Search Console data with their permission, for security reasons or when the law requires it.

Adding a SERP provider

A provider is a small adapter that turns one keyword check into API requests and returns the organic results. The interface (src/lib/serp/parse.ts and src/seo/types.ts):

interface SerpCheckInput {
  phrase: string; country: string; language: string;   // "US", "en" (Google gl / hl via googleGl() / googleHl())
  device: "desktop" | "mobile"; location: string;       // "" = whole country
  depth: 10 | 20 | 50 | 100; domain: string; competitors: string[];
}
interface RankProvider {
  id: string;      // stored in rankings.provider (max 20 characters)
  name: string;
  check(input: SerpCheckInput): Promise<ProviderResult>;  // RankResult + { requests: number }
}
// Throw new SerpProviderError(message, "config" | "quota" | "network" | "response") for problems.
// "config" pauses all checks for 30 minutes, "quota" for 1 hour; the others retry the keyword later.
  1. Create src/lib/serp/providers/myserp.ts with createMySerpProvider(options: { apiKey: string; fetch: SerpFetch; timeoutMs?: number }): RankProvider. Use options.fetch (it applies the private-address guard, timeouts and a size cap, and lets tests replay recorded answers). For each page 1…pagesFor(input.depth): request 10 results, turn an unsuccessful answer into an error with httpError("MySERP", status, errorMessage(json, text)), pass the organic results ({ url, title }, in order) to a ResultCollector and stop when collector.done() or a page is empty. Detect SERP features on page 1. Return collector.result(features, requests, credits). Copy serper.ts as a starting point.
  2. In src/lib/serp/index.ts add the id to REAL_PROVIDER_IDS, an entry to PROVIDERS (name, key label and placeholder, website, a short cost note), a case in envKey() (e.g. MYSERP_API_KEY, the name the admin page lists) and in createProvider().
  3. The admin page, the test button, usage and pauses work automatically. Run npm run typecheck, then test the key with Test connection.

Adding an audit check

Add pageCheck(code, severity, category, test) or siteCheck(…) to the matching list in src/lib/audit/checks/ (codes are lower-case snake_case and are stored with the issues), and the texts audit.issue.<code>, audit.issue.<code>.help and audit.issue.<code>.fix in messages.ts. A test returns true or an object with details for affected pages. If the check needs new page data, extract it in src/lib/audit/parse.ts and add it to CrawledPage (src/lib/audit/types.ts). The health score and the reports include new checks automatically.

Build fails with “[badge] build failed” or “exceeds the 2048 B budget”Dev dependencies (esbuild, Tailwind, TypeScript) are missing: run npm install (not --omit=dev) before building. The budget message only appears if you changed the badge and it grew above 2 KB gzipped.
“storage folder is writable” failsGive the app user write access: chmod -R 775 storage (and chown it to the user running Node.js).
Database connection failsCheck host (usually localhost or 127.0.0.1), port 3306, and that the user has all privileges on the database. On cPanel the database and username include your account prefix, e.g. myacc_searchzen. Cloud databases need Use SSL.
SQLite option failsSQLite needs Node.js 22.13+. Choose a newer Node.js version in your hosting panel or use MySQL.
Can't sign in after installing on HTTPS behind a proxyMake sure the proxy sends X-Forwarded-Proto and Host headers (see the Nginx example).
Users get “Too many requests” on sign-inBehind Cloudflare + Nginx set TRUSTED_PROXY_HOPS=2, so each visitor has their own limit.
Plan payments are not activatedFor Stripe, check the endpoint /api/payments/stripe/webhook and its signing secret in Settings → Payments, and the delivery log in Stripe.
I forgot the admin passwordUse “Forgot password” (needs SMTP). Otherwise ask another administrator, or delete storage/installed.lock, restart, and run the installer again with the same database and admin email: the installer sets the new password on the existing account and keeps all data.
